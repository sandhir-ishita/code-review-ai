
## 1. AI System Overview

The AI component is responsible for analyzing submitted source code and
generating an intelligent code review.

The system will use a pre-trained Large Language Model (LLM) through an
external API.

The LLM will not directly control the application.

The backend will:

1. Prepare the input.
2. Provide relevant context to the LLM.
3. Request structured output.
4. Validate the LLM response.
5. Normalize the response.
6. Combine AI results with static analysis.
7. Store the final review.

---

# 2. Why Use Static Analysis + AI?

The system will not depend entirely on the LLM.

Instead, it will combine:

```text
Static Analysis
      +
AI Analysis
      =
Final Code Review

Static analysis is useful for detecting deterministic issues such as:

Syntax errors
ESLint violations
Unused variables
Undefined variables
Complexity problems
Known code patterns

AI analysis is useful for understanding:

Developer intent
Logical problems
Potential bugs
Requirement compliance
Maintainability
Code design
Suggestions
Human-readable explanations

Using both approaches makes the system more reliable than using either
approach alone.

4. AI Input

The LLM will receive relevant information about the code.

The input will contain:

Source Code

The actual code submitted by the user.

Programming Language

Example:

JavaScript
User Requirements

Optional requirements provided by the user.

Example:

Create an API that returns all active users.
Static Analysis Results

Results generated by ESLint or other analysis tools.

Example:

{
  "errorCount": 2,
  "warningCount": 3,
  "issues": [
    {
      "line": 10,
      "severity": "warning",
      "rule": "no-unused-vars",
      "message": "Variable is unused"
    }
  ]
}
5. AI Context Structure

The backend should construct a structured context similar to:

Language:
JavaScript

Requirements:
Create a function that calculates the total price.

Static Analysis:
2 warnings
1 error

Source Code:
function calculateTotal(items) {
    ...
}

The backend should avoid sending unnecessary information to the LLM.

6. Prompt Design

The prompt should clearly define the role of the AI.

Example:

You are an expert software engineer performing a code review.

Analyze the provided source code carefully.

Your review must focus on:

1. Bugs
2. Security
3. Performance
4. Code quality
5. Maintainability
6. Edge cases
7. Requirement compliance

Do not invent issues that are not supported by the code.

If you are uncertain about an issue, clearly indicate the uncertainty.

Return the result strictly in the requested JSON structure.

The prompt should also contain the code and requirements.

7. AI Output

The LLM should return structured JSON.

Example:

{
  "category": "Backend",
  "summary": "The implementation is functional but lacks input validation.",
  "scores": {
    "quality": 78,
    "security": 65,
    "performance": 82,
    "maintainability": 75,
    "requirements": 80
  },
  "strengths": [
    "Simple implementation",
    "Readable structure"
  ],
  "weaknesses": [
    "Missing input validation"
  ],
  "issues": [
    {
      "type": "BUG",
      "severity": "HIGH",
      "title": "Missing null validation",
      "description": "The function may fail when the input is null.",
      "lineNumber": 12,
      "suggestion": "Validate the input before accessing its properties."
    }
  ],
  "recommendations": [
    "Add input validation",
    "Improve error handling"
  ]
}
8. AI Response Schema

The backend will define a strict schema for the AI response.

The schema will validate:

Category
Summary
Scores
Strengths
Weaknesses
Issues
Recommendations

Zod will be used for schema validation.

Conceptually:

LLM Response
     |
     v
Zod Schema
     |
     +---- Invalid ----> Handle / Retry
     |
     v
Valid Data

The application must never assume that the LLM response is valid.

9. AI Score Validation

The backend must validate AI-generated scores.

All scores must satisfy:

0 <= score <= 100

Invalid examples:

quality = -20
security = 150
performance = "excellent"

These responses must be rejected or normalized before being stored.

10. AI Issue Validation

Every issue should contain:

type
severity
title
description
lineNumber
suggestion

Valid issue types:

BUG
SECURITY
PERFORMANCE
CODE_QUALITY
MAINTAINABILITY
REQUIREMENT

Valid severity values:

CRITICAL
HIGH
MEDIUM
LOW
INFO

The backend should validate these values.

11. Requirement Analysis

If requirements are provided, the AI must explicitly compare the code against
them.

The AI should identify:

Satisfied Requirements
Partially Satisfied Requirements
Missing Requirements
Violations

Example:

{
  "requirementAnalysis": {
    "score": 75,
    "satisfied": [
      "API endpoint exists"
    ],
    "partial": [
      "Input validation is incomplete"
    ],
    "missing": [
      "Authentication is not implemented"
    ]
  }
}

If no requirements are provided, the requirement score should be marked as
not applicable instead of inventing requirements.

12. Code Classification

The AI should classify the code based on its purpose.

Possible categories:

Frontend
Backend
API
Authentication
Database
Algorithm
Data Structure
Utility
Testing
Security
Configuration

The category should be based on the actual code rather than assumptions.

13. AI + Static Analysis Combination

The final review will combine both sources.

Example:

Static Analysis
      |
      +---- 3 ESLint issues
      |
      v
                  +----------------+
                  | Review Service |
                  +----------------+
                           ^
                           |
AI Analysis                |
      |                    |
      +---- 2 logical ----+
            issues

The Review Service will merge both results.

Static analysis should be treated as deterministic evidence.

AI analysis should provide reasoning, interpretation and recommendations.

14. Duplicate Issue Handling

The same issue may be detected by both static analysis and AI.

Example:

ESLint:
Unused variable at line 10

AI:
Variable at line 10 is never used

The Review Service should attempt to merge duplicate issues.

The final review should avoid showing the same issue multiple times.

15. Confidence and Uncertainty

AI-generated findings may not always be certain.

The system should encourage the AI to distinguish between:

Confirmed
Likely
Potential

For example:

Severity: MEDIUM
Confidence: POTENTIAL

The application should avoid presenting uncertain AI findings as guaranteed
bugs.

16. Hallucination Prevention

The AI prompt should instruct the model:

Do not invent bugs.
Do not invent requirements.
Do not claim that code was executed if it was not executed.
Do not claim that a database was accessed if it was not accessed.
Base findings on the provided code and context.
Clearly state uncertainty.

The system should also limit the context sent to the model to relevant
information.

17. Code Execution Policy

The system will NOT directly execute arbitrary user-submitted code.

This is an important security requirement.

The initial version will rely on:

Static Analysis
+
AI Analysis

rather than executing user code.

If code execution is introduced in the future, it must happen inside a
properly isolated sandbox with:

CPU limits
Memory limits
Execution timeout
Network restrictions
Filesystem restrictions
Process isolation
18. Large Code Handling

LLMs have context limits.

The system should therefore enforce a maximum submission size.

For the initial MVP, code that exceeds the configured limit should be rejected
with an appropriate validation error.

Future versions may support:

Large Repository
      |
      v
File Selection
      |
      v
Relevant Code Extraction
      |
      v
Chunking
      |
      v
Multiple AI Calls
      |
      v
Final Aggregated Review
19. AI Failure Handling

The AI API can fail.

Possible failures:

Network error
API timeout
Rate limit
Invalid API key
Provider error
Malformed response

The backend should handle these gracefully.

Example:

AI API
  |
  +---- Success ----> Validate Response
  |
  +---- Timeout ----> Retry / Fail
  |
  +---- Rate Limit -> Retry later / Fail
  |
  +---- Invalid ----> Error Handling

The user should receive a meaningful error instead of a raw provider error.

20. Retry Strategy

The system may retry temporary AI failures.

Retryable errors may include:

Timeout
Temporary network failure
Temporary provider failure

Permanent errors should not be repeatedly retried.

Examples:

Invalid API Key
Invalid Request
Unsupported Model

These should fail immediately and be logged.

21. AI Model Abstraction

The application should not tightly couple the entire codebase to one LLM
provider.

Instead, the backend should expose an AI service abstraction.

Conceptually:

Review Service
      |
      v
AI Service Interface
      |
      +---- Provider A
      |
      +---- Provider B
      |
      +---- Local Model

This allows the LLM provider to be changed later without rewriting the
review system.

22. AI Service Responsibility

The AI Service should be responsible for:

Building AI prompts
Sending requests to the LLM
Receiving responses
Parsing responses
Handling provider errors
Returning normalized AI data

The AI Service should NOT:

Directly modify database records
Handle HTTP requests
Manage authentication
Calculate unrelated application logic
23. Review Service Responsibility

The Review Service should coordinate the complete review.

It should:

Fetch submission.
Validate submission.
Run static analysis.
Call AI Service.
Validate AI result.
Merge analysis results.
Remove duplicate issues.
Calculate final scores.
Store review.
Return final review.

25. AI Cost Management

AI requests may have usage costs.

The system should control AI usage using:

Request rate limiting
Maximum code size
Maximum requirement size
Per-user review limits
Efficient prompts
Avoiding unnecessary duplicate requests

Future versions may implement user-specific quotas.

26. AI Observability

The system should log important AI events without logging sensitive source
code unnecessarily.

Useful metadata includes:

Review ID
User ID
Model
Request duration
Token usage if available
AI status
Retry count
Error type

Sensitive code should not be unnecessarily written to application logs.

27. AI Security

The system should protect:

LLM API keys
User source code
User requirements
AI responses

API keys must be stored in environment variables.

Example:

LLM_API_KEY=...

The API key must never be committed to GitHub or exposed to the frontend.

28. AI Design Principles

The AI subsystem should follow these principles:

Do not trust AI output blindly.
Validate all AI responses.
Combine deterministic analysis with AI reasoning.
Do not execute arbitrary user code.
Keep the AI provider behind an abstraction layer.
Handle AI failures gracefully.
Control AI usage and costs.
Avoid unnecessary sensitive logging.
Clearly distinguish uncertain findings.
Keep AI responsibilities separate from business logic.
