# AI Code Review System - Database Design

## 1. Database Overview

The application will use PostgreSQL as the primary relational database.

Prisma ORM will be used by the Node.js backend to communicate with
PostgreSQL.

The database is responsible for storing:

- User accounts
- Authentication sessions
- Projects
- Code submissions
- Static analysis results
- AI reviews
- Review issues

The database should maintain relationships between these entities so that
users can access their own projects and review history.

---

## 2. Main Entities

The initial database will contain the following entities:

1. User
2. RefreshToken

4. CodeSubmission

4. User

The User table stores registered application users.

Fields
Field	Type	Description
id	UUID	Unique user identifier
name	String	User's name
email	String	Unique email address
passwordHash	String	Hashed password
createdAt	DateTime	Account creation time
updatedAt	DateTime	Last update time
Rules
email must be unique.
Password must never be stored in plain text.
passwordHash contains the bcrypt hash.
A user can own multiple projects.
A user can have multiple refresh tokens.
5. RefreshToken

The RefreshToken table stores refresh tokens used to maintain authenticated
sessions.

Fields
Field	Type	Description
id	UUID	Unique token identifier
userId	UUID	Reference to User
tokenHash	String	Hashed refresh token
expiresAt	DateTime	Token expiration time
createdAt	DateTime	Token creation time
revokedAt	DateTime	Token revocation time
Relationship
User
 |
 +---- RefreshToken
 |
 +---- RefreshToken
 |
 +---- RefreshToken

One user can have multiple active or historical sessions.

6. Project

The Project table represents a coding project created by a user.

Fields
Field	Type	Description
id	UUID	Unique project identifier
userId	UUID	Project owner
name	String	Project name
description	String	Optional project description
createdAt	DateTime	Creation time
updatedAt	DateTime	Last update time
Relationship
User
 |
 +---- Project
       |
       +---- CodeSubmission
       +---- CodeSubmission
       +---- CodeSubmission

A user can create multiple projects.

Each project belongs to exactly one user.

7. CodeSubmission

The CodeSubmission table stores source code submitted by the user.

Fields
Field	Type	Description
id	UUID	Unique submission identifier
projectId	UUID	Related project
code	Text	Submitted source code
language	String	Programming language
requirements	Text	Optional user requirements
createdAt	DateTime	Submission time
Example
Project
   |
   +---- Submission #1
   |       Language: JavaScript
   |
   +---- Submission #2
   |       Language: TypeScript
   |
   +---- Submission #3
           Language: JavaScript

The source code will be stored as text.

The initial supported languages are:

JavaScript
TypeScript
8. StaticAnalysis

The StaticAnalysis table stores results generated by static code analysis
tools such as ESLint.

Fields
Field	Type	Description
id	UUID	Unique analysis identifier
submissionId	UUID	Related code submission
tool	String	Analysis tool used
status	String	Analysis status
errorCount	Integer	Number of errors
warningCount	Integer	Number of warnings
results	JSON	Detailed analyzer output
createdAt	DateTime	Analysis time
Example
{
  "tool": "eslint",
  "errorCount": 2,
  "warningCount": 4,
  "results": [
    {
      "line": 12,
      "rule": "no-unused-vars",
      "severity": "warning",
      "message": "Variable is unused"
    }
  ]
}

The results field uses PostgreSQL JSON/JSONB storage.

9. Review

The Review table stores the final result of the code review.

A submission may have multiple reviews because the same code may be reviewed
again using different AI models, prompts or updated requirements.

Fields
Field	Type	Description
id	UUID	Unique review identifier
submissionId	UUID	Related code submission
status	String	Review status
overallScore	Integer	Overall score from 0-100
qualityScore	Integer	Code quality score
securityScore	Integer	Security score
performanceScore	Integer	Performance score
maintainabilityScore	Integer	Maintainability score
requirementScore	Integer	Requirement compliance score
category	String	Detected code category
summary	Text	Overall review summary
strengths	JSON	Code strengths
weaknesses	JSON	Code weaknesses
recommendations	JSON	Improvement recommendations
model	String	LLM model used
createdAt	DateTime	Review creation time
completedAt	DateTime	Review completion time
10. Review Status

14. Relationships
User → Project

One user can have many projects.

User 1 -------- N Project
User → RefreshToken

One user can have multiple refresh tokens.

User 1 -------- N RefreshToken
Project → CodeSubmission

One project can contain multiple code submissions.

Project 1 -------- N CodeSubmission
CodeSubmission → StaticAnalysis

A submission can have static analysis results.

CodeSubmission 1 -------- N StaticAnalysis

Multiple analysis runs are allowed so that analysis can be repeated later.

CodeSubmission → Review

One code submission can have multiple reviews.

CodeSubmission 1 -------- N Review
Review → Issue

One review can contain multiple issues.

16. Data Ownership and Authorization

The database relationships will help enforce ownership.

Example:

Logged-in User
      |
      v
Project
      |
      v
Code Submission
      |
      v
Review
      |
      v
Issue

Before accessing a project, submission or review, the backend must verify
that the resource belongs to the authenticated user.

The backend must never rely only on an ID supplied by the client.

17. Data Integrity

The database should enforce:

Unique user email.
Foreign key relationships.
Required fields.
Valid references.
Appropriate cascade behavior.
Timestamps for important entities.

Deleting a project should also handle its related submissions, analyses,
reviews and issues according to the defined Prisma relation behavior.

18. Database Design Goals

The database design should provide:

Data consistency
Clear relationships
Easy querying
Secure ownership boundaries
Review history
Support for repeated analysis
Future scalability
Compatibility with Prisma ORM
